# F8 · Propuesta de staging de WiseLoad

F8-01 iniciada el 08/11/2026 desde el cierre local de F7, `3632de3`. El objetivo es entregar la web y el servidor de WiseLoad a un grupo invitado y un APK conectado al mismo servidor. El promotor autorizó iniciar el ensayo gratuito en Virginia, con una validación breve y cuentas de prueba, y retiró las pruebas de rendimiento. El aprovisionamiento está en curso. Las políticas para estudiantes reales y la aprobación de la versión para invitados se revisan por separado.

## Puesta en marcha del ensayo gratuito

1. Desde el panel de Supabase, crear un proyecto Free exclusivo `wiseload-staging` en **East US (North Virginia)**. En **Connect**, copiar la conexión de **Session pooler** (puerto 5432). Descargar el certificado CA de Supabase desde **Database Settings → SSL Configuration**. [Conexión a Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres), [TLS verificado](https://supabase.com/docs/guides/platform/ssl-enforcement).
2. Guardar un archivo local ignorado `.local/staging-db.env`, separado de `.env`. Incluir `WISELOAD_ENV=staging`, `SUPABASE_URL` y `MIGRATION_DATABASE_URL` para `postgres.<ref>`. Incluir `DATABASE_URL` y `IDENTITY_DATABASE_URL` para `cw_runtime.<ref>` y `cw_identity.<ref>` con contraseñas diferentes de 24 bytes aleatorios en hexadecimal. Conservar el host del panel y terminar las tres URL con `/postgres?sslmode=verify-full`. Indicar el archivo CA al proceso con `NODE_EXTRA_CA_CERTS` si se necesita.
3. Con Node 24 desde la raíz del repositorio, ejecutar una vez el bootstrap. Ejecutar las migraciones por separado. Repetir únicamente la migración para comprobar idempotencia.

   ```sh
   node --env-file=.local/staging-db.env --import tsx scripts/backend/staging-bootstrap.ts
   node --env-file=.local/staging-db.env --import tsx scripts/backend/migrate.ts
   ```

4. En Render, vincular el repositorio y preparar un **Web Service** llamado `wiseload-staging` en **Virginia**, con plan **Free**, runtime **Docker**, directorio raíz del repo y Dockerfile `infra/staging/Dockerfile`. Elegir la rama de staging y desactivar auto-deploy. Configurar la ruta de salud `/api/v1/health/ready`. El mismo proceso entrega el build web y la API. [Configuración Docker en Render](https://render.com/docs/docker).
5. En Render, cargar `WISELOAD_ENV=staging`, `PUBLIC_APP_ORIGIN` con la URL HTTPS exacta asignada, `SUPABASE_URL`, `SUPABASE_ANON_KEY` con la clave pública de Supabase, `CREDENTIAL_ENCRYPTION_KEY` nueva de 32 bytes en hexadecimal, `DATABASE_URL`, `IDENTITY_DATABASE_URL` y `STAGING_ALLOWED_EMAILS` con los correos de prueba separados por comas. Si se necesita la CA, subirla como archivo secreto y configurar `NODE_EXTRA_CA_CERTS` con su ruta. El secreto de migración pertenece al paso 3. Carga e IA permanecen cerradas durante el ensayo de arranque.
6. Desplegar el commit aprobado. Confirmar que la raíz entrega la web conectada, readiness devuelve 200 y una cuenta fuera de la lista queda bloqueada. En Supabase, poner la URL pública de Render como Site URL y configurar el proveedor Google y su retorno exacto. Activar `GOOGLE_AUTH_ENABLED=true` en Render después de configurar el proveedor. Para Calendar, cargar `CALENDAR_CLIENT_ID` y `CALENDAR_CLIENT_SECRET` del cliente separado en Render. Para OTP, conservar destinatarios autorizados y la plantilla de código. La prueba debe usar datos sintéticos.
