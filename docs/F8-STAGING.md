[Tarifa de cómputo Render](https://render.com/articles/set-up-self-hosted-github-actions-runners-on-render), [Supabase Pro](https://supabase.com/pricing).

## Configuración propuesta

| Recurso | Configuración de referencia |
|---|---|
| Entorno y región | `wiseload-staging` en Render Virginia y Supabase East US (North Virginia), región específica `us-east-1`. Medir desde Lima antes de fijar región de producción. [Regiones de Render](https://render.com/docs/regions), [regiones de Supabase](https://supabase.com/docs/guides/platform/regions). |
| Artefacto web/API | Una imagen Linux con Node 24.22.2, dependencias fijadas por lockfile y usuario sin root. Fastify servirá `dist` y `/api/v1` bajo el mismo origen. Publicar solo el SHA probado desde un workflow manual de staging, con auto-deploy desactivado y `/api/v1/health/ready` como comprobación de salud. El CI existente conserva `pull_request` y `push` solo a `main`. |
| Configuración desplegada | Añadir un modo de staging explícito que escuche en `0.0.0.0` con el `PORT` del hosting y exija un origen HTTPS exacto. Las guardas actuales bloquean el entorno remoto y el arranque depende de Docker. Mantener las guardas de desarrollo y el gate de producción. El dominio exacto se fija cuando Render asigne la URL. |
| Supabase | Un proyecto y bucket privado exclusivos. TLS con verificación para PostgreSQL. Probar conexión directa o pooler en modo sesión según conectividad. Conservar roles separados `cw_runtime`, `cw_identity` y `cw_migrator`, RLS forzada y dos pools de hasta cinco conexiones por proceso. La credencial de migración vive solo en el paso manual de migración. Probar bootstrap y grants contra el servicio gestionado antes del primer deploy. |
| Acceso y secretos | Restringir el alta y el acceso a cuentas sintéticas previamente autorizadas. Definir `PUBLIC_APP_ORIGIN` y `OAUTH_CALLBACK_ORIGIN` con el mismo HTTPS de staging. Guardar URL/credenciales de DB, claves Supabase de servidor, clave nueva de cifrado y secretos OAuth en sus paneles o entorno protegido de GitHub, según consumidor. Ningún secreto de staging en Git, Vite ni logs. |
| Google | Dos clientes web exclusivos de staging, uno para identidad y otro para Calendar. Sign-in registra en Google el callback del proyecto Supabase y en Supabase permite el retorno exacto a `https://<staging>/api/v1/auth/google/callback`. Calendar registra `https://<staging>/api/v1/calendar/callback` en Google y pide `calendar.calendarlist.readonly`, `calendar.events.freebusy` y `calendar.events.readonly`. Añadir usuarios de prueba. En modo Testing, la autorización de Calendar puede caducar a los siete días. [Supabase Google](https://supabase.com/docs/guides/auth/social-sign-in/auth-google), [Google Testing](https://support.google.com/cloud/answer/15549945). |
| SMTP | Plantilla con código OTP y destinatarios internos en la prueba inicial. Si se aprueba la prueba externa, verificar DNS y configurar SMTP de Resend en Supabase con credenciales de staging. Conservar el HTTPS web de Render aunque el remitente use su propio dominio. |
| Parser PDF/XLSX | La carga empieza deshabilitada en staging hasta verificar un ejecutor aislado con el mismo límite de 30 s, 384 MiB, una extracción a la vez y protección de red, archivos y credenciales. Evaluar Podman sin privilegios en el plan objetivo con archivos sintéticos. Verificar que el entorno aplica de verdad los límites, el bloqueo de red, la ausencia de secretos, solo lectura y la terminación en timeout. Si falla la prueba, el alta manual queda disponible y la validación documental desplegada sigue pendiente hasta probar otro aislamiento aprobado. [Prueba de contenedores rootless en Render](https://render.com/articles/set-up-self-hosted-github-actions-runners-on-render). |
| Premium | Primera pasada con dobles. Para una corrida real posterior, usar credenciales de staging, fixture sintético, consentimiento de prueba y reserva de presupuesto antes de la primera solicitud. Mantener el alta manual y desactivar las llamadas al terminar. |

## Decisiones a revisar antes de aprovisionar

- **D-14.** Propuesta de ensayo web sintético de USD 0 en Virginia, Render Hobby/Free y Supabase Free, con URL de Render y OTP interno. Revisar después si hace falta medir con el plan de 2 GB o verificar envío externo. El coste de ambos depende de decisiones separadas.
- **D-15 para staging sintético.** Usar cuentas de prueba y calendario de prueba. Purga al terminar el ensayo, con revisión como máximo a los 30 días desde la creación. Copias cifradas y objetos sintéticos de recuperación con caducidad de siete días. Excluir de las copias los originales temporales de importación, las sesiones y las credenciales de proveedor. La recuperación restablece datos académicos de prueba y requiere una autenticación nueva. Si se habilita la extracción, borrar el original al finalizar y pedir una nueva subida para un análisis posterior. La política para estudiantes reales, consentimientos, borrado de cuenta y respaldos de producción se revisa por separado antes del piloto.

El expediente de F8-06 debe distinguir el arranque con planes gratuitos, la medición en el tamaño objetivo y las pruebas pendientes de proveedores o aislamiento. El smoke de staging acredita la web desplegada. Android conectado conserva AM-01.
