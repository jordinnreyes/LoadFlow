# F8 · Candidato de liberación web de WiseLoad

El promotor eligió registro con cualquier cuenta de Google y conservar una URL de Render. Producción tendrá su propio servicio, proyecto Supabase y proyecto OAuth. El nombre tentativo del servicio es `wiseload`. Registrar la URL que asigne Render antes de crear callbacks o iniciar la verificación de Google. La apertura al público se decide sobre un commit concreto en G-PROD.

## Qué se publica

- Primera web pública con acceso Google, cuentas que comienzan vacías, gestión académica, planificación y disponibilidad manual. Los endpoints y el formulario OTP quedan deshabilitados en el modo de producción de esta release.
- Calendar tiene un cliente OAuth distinto. La primera apertura pública incluye tanto el registro con Google como Calendar. La revisión de Calendar puede hacerse con cuentas invitadas mientras el registro público sigue cerrado.
- La carga de documentos, Premium y el APK conectado conservan sus comprobaciones separadas. El ensayo de restauración de esta release se concentra en PostgreSQL y en datos académicos. Las copias de objetos se comprobarán antes de habilitar carga.

## Configuración en orden

1. Crear un segundo proyecto **Supabase Free** en North Virginia. Mantener Data API y exposición automática de tablas desactivadas. Generar credenciales nuevas, descargar la CA y usar el **Session pooler** en 5432 con `sslmode=verify-full`. En una configuración de administración local separada, fijar `WISELOAD_ENV=production`, `SUPABASE_URL`, `STAGING_SUPABASE_PROJECT_REF` y `PRODUCTION_SUPABASE_PROJECT_REF`. Las referencias deben ser distintas. Repetir [el bootstrap y la migración](F8-STAGING.md#puesta-en-marcha-del-ensayo-gratuito) contra este proyecto nuevo. Mantener la credencial de migración fuera de Render. [Cupos de Supabase Free](https://supabase.com/pricing).
2. Preparar otro **Render Web Service** en Virginia con plan **Free**, runtime Docker, mismo `infra/staging/Dockerfile`, auto-deploy apagado y readiness `/api/v1/health/ready`. Seleccionar el SHA del candidato. Fijar los secretos de base y cifrado de producción y cargar la CA. Usar la URL asignada como `PUBLIC_APP_ORIGIN`. El primer arranque es una revisión cerrada, con `PRODUCTION_ALLOWED_EMAILS` para las cuentas de prueba y `PUBLIC_REGISTRATION_ENABLED=false`. Mantener `PRODUCTION_CALENDAR_ENABLED=false`. Fijar `PUBLIC_PRIVACY_CONTACT` con el buzón que atenderá solicitudes. [Render Free y sus límites](https://render.com/docs/free).
3. En el proyecto de **Google Cloud de producción**, crear un cliente web de identidad. Usar el origen de producción en JavaScript origins y el callback `https://<ref-prod>.supabase.co/auth/v1/callback` en Google. Poner el ID y secreto en el proveedor Google de Supabase. En URL Configuration, Site URL es el origen de Render y el redirect permitido es `<origen>/api/v1/auth/google/callback`. Poner `GOOGLE_AUTH_ENABLED=true` en Render y habilitar el proveedor de identidad. [Separación OAuth y políticas](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance).
4. Verificar que dos cuentas de revisión distintas aterrizan en un Tablero vacío, que una actividad creada por la primera persiste después de volver a entrar y que la segunda no puede verla. Confirmar logout, protección 401, bloqueo de OTP y disponibilidad de `/privacidad`. Probar retorno tras cancelar Google y revisar las alertas básicas del hosting. Registrar hora, SHA y resultados, sin incluir correos ni datos académicos reales.
5. Resolver D-15 y revisar el expediente G-PROD. Con la verificación de Calendar aprobada y su prueba cerrada en producción completada, aplicar `PUBLIC_REGISTRATION_ENABLED=true` y `PRODUCTION_CALENDAR_ENABLED=true` juntos al SHA autorizado. Comprobar el ingreso y la conexión con Calendar desde una cuenta fuera de ambas listas de revisión. Si falla alguna comprobación, devolver ambas variables a `false` en un solo despliegue. Si falla el artefacto, volver a un deploy anterior compatible del mismo servicio o suspender la apertura. Conservar la base y ejecutar una corrección aprobada si cambia el esquema.

## Google Calendar público

El promotor confirmó que Calendar funcionó en staging. Una consulta de solo lectura confirmó la existencia de conexión y de snapshot de ocupación. El sitio de producción puede servir `/privacidad` y una etiqueta de Search Console con `GOOGLE_SITE_VERIFICATION`. En Search Console, probar **URL prefix** con la URL exacta de Render y el método **HTML tag**. Después, comprobar que Google Auth Platform acepta ese host como dominio autorizado del proyecto de producción. Search Console y la aceptación del dominio para OAuth son comprobaciones distintas. [Verificar propiedad](https://support.google.com/webmasters/answer/9008080), [dominios autorizados](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance#only-use-domains-you-own).

La portada `/inicio` y la política `/privacidad` del servicio web respondieron HTTP 200 con el contenido correcto. Tras otro rechazo de Google se preparó un sitio estático para Branding. Render Free puede tardar alrededor de un minuto en reactivarse después de 15 minutos sin tráfico. Durante ese periodo Render responde a `/robots.txt` con `Disallow: /`. El sitio estático sirve las mismas páginas desde la CDN y enlaza al acceso en el servicio web existente. [Requisitos de la página principal](https://support.google.com/cloud/answer/13807376) · [Comportamiento de Render Free](https://render.com/docs/free#automatic-robots-txt-responses).

En Render, seleccionar **New → Static Site**, repositorio `jordinnreyes/LoadFlow`, rama `codex/f8-public-release`, directorio raíz vacío, **Build Command** `node scripts/backend/build-public-pages.mjs` y **Publish Directory** `dist/public-site`. Configurar `SKIP_INSTALL_DEPS=true` y `PUBLIC_PRIVACY_CONTACT` con el correo público de WiseLoad. El build solo necesita Node 24 y no necesita credenciales de la aplicación. [Static Sites de Render](https://render.com/docs/static-sites).

Tras el primer despliegue, agregar la URL que asigne Render a Search Console como **Prefijo de URL** con la cuenta propietaria o editora del proyecto OAuth. Elegir **Etiqueta HTML**, guardar el nuevo valor `content` como `GOOGLE_SITE_VERIFICATION` en el sitio estático y reconstruir. Verificar la propiedad y comprobar que la raíz y `/privacidad.html` devuelven el contenido correcto sin sesión. Añadir el nuevo host a Dominios autorizados antes de cambiar las URLs de Branding. Usar **WiseLoad** como nombre, la raíz del sitio estático como página principal y `/privacidad.html` del mismo host como política. Conservar los dominios de los clientes OAuth y su verificación. Si Google sigue mostrando problemas con las páginas verificadas, usar **Ver problemas → Solicitar revisión adicional**. [Verificación de marca](https://support.google.com/cloud/answer/15549049) · [Dominios autorizados](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance#only-use-domains-you-own).

| Permiso de solo lectura | Uso en WiseLoad |
|---|---|
| `calendar.calendarlist.readonly` | Mostrar los calendarios disponibles y permitir que la persona elija cuáles usar. |
| `calendar.events.freebusy` | Consultar los tramos ocupados que el plan debe respetar. |
| `calendar.events.readonly` | Obtener los títulos cuando la persona activa su visualización. |

En Google Cloud, usar otro cliente web para Calendar con callback `<origen>/api/v1/calendar/callback`. En el expediente incluir el inicio y la política de privacidad del mismo origen, el contacto, la justificación anterior y el enlace al video en inglés y no listado. El video usa una cuenta y un calendario sintéticos y muestra el consentimiento, selección, sincronización, bloques, títulos y desconexión. Google solicita que se vea el ID del cliente OAuth del proyecto que se envía. Configurar `CALENDAR_CLIENT_ID` y `CALENDAR_CLIENT_SECRET` en Render y hacer la prueba cerrada con el registro limitado a los revisores autorizados. Para la apertura pública, comprobar que el proyecto OAuth acepta usuarios externos en producción y que Verification Center aprobó los tres permisos. [Guía de verificación de scopes sensibles](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification).

## Datos y recuperación

- La página de privacidad describe cuenta, datos académicos, ocupación, títulos, cifrado de credenciales y canal de solicitudes. El promotor indicó el buzón público de soporte para `PUBLIC_PRIVACY_CONTACT` y eligió atender solicitudes de borrado en un máximo de 15 días, con copias cifradas que caducan a los siete días. La política pública se revisa contra el procedimiento de borrado antes de exponerla.
- Usar copias cifradas de DB con acceso de operador y guardar las claves por separado. Excluir sesiones y credenciales de OAuth del procedimiento de recuperación de usuarios y exigir nuevo inicio de sesión cuando corresponda. Aplicar la caducidad aprobada y mantener el registro de solicitudes fuera de las copias restauradas. [Backups de Supabase](https://supabase.com/docs/guides/platform/backups).
- La entrada pública de OAuth limpia transacciones vencidas y limita a 250 los inicios conservados por la ventana de diez minutos. Un ensayo aislado con PostgreSQL comprobó la limpieza y el rechazo HTTP 429 al llegar al límite. Falta confirmar alertas y observar el comportamiento al arrancar el servicio de revisión.

### Evidencia y límites

El ensayo de recuperación aplicó las 16 migraciones a una base temporal con una identidad y una actividad ficticias. `pg_dump -Fc` y `pg_restore --exit-on-error` recuperaron el registro de migraciones y la actividad en otra base. Al conectar como `cw_runtime`, el propietario vio una actividad y un segundo contexto vio cero. Se retiraron ambas bases temporales. Este ensayo usa el identificador de Auth como fixture y cubre el esquema académico, su registro de migraciones y RLS.

### Borrado de una cuenta de la primera release

1. Verificar la identidad de la persona solicitante en el buzón de soporte y confirmar el UUID de Auth en el proyecto de producción. Registrar solo el identificador necesario, la fecha y el estado en el registro privado de solicitudes, fuera de las copias que puedan restaurarse.
2. Ejecutar la vista previa con `node --env-file=.local/production-db.env --import tsx scripts/backend/account-removal.ts ID`. El operador recibe solo un indicador de existencia. Si quedan credenciales de Calendar, revocar y comprobar su retirada antes del borrado. Si hay documentos, usar el procedimiento de Storage correspondiente antes de continuar. Esta primera release mantiene desactivada la carga de documentos.
3. Suspender el servicio de producción y confirmar que los workers se detuvieron. Con `ACCOUNT_REMOVAL_MAINTENANCE=true` en el proceso del operador, ejecutar el mismo comando con `ID --apply ID`. El script borra por propietario en una sola transacción y elimina la identidad Auth y las sesiones BFF. Repetir la vista previa y confirmar que la cuenta ya no existe. Reactivar el servicio tras revisar el resultado. [Eliminación de usuarios en Supabase](https://supabase.com/docs/guides/auth/managing-user-data#deleting-users).
4. Mantener la solicitud en el registro protegido hasta que caduquen las copias correspondientes. Si se restaura una copia anterior, reaplicar los borrados registrados antes de reactivar el servicio.

El ensayo local usó dos cuentas sintéticas en una base temporal con las 16 migraciones. Se comprobó el bloqueo cuando queda una credencial de Calendar, la revisión sin cambios, la eliminación de una cuenta y su sesión, la repetición segura y la conservación de la segunda cuenta.

En el servicio de revisión, el promotor confirmó que la prueba de acceso con Google funcionó. Supabase registró dos cuentas vinculadas con Google. Un ensayo en una transacción revertida contra Auth gestionado de producción comprobó la vista previa, el borrado de una cuenta sintética con un periodo, una actividad y una sesión, la repetición segura y la conservación de las dos cuentas de revisión. El ensayo no suspendió Render ni emitió sesiones de Google. La portada y `/privacidad` devolvieron 200. La portada todavía no servía la etiqueta de Search Console.

Para la primera liberación quedan la confirmación de alertas, el consentimiento y la sincronización de Calendar con el cliente de producción y la verificación externa de sus permisos. El promotor solicitó abrir ambas funciones juntas tras la revisión cerrada.
